# 编程到底难在哪里？

---

很多人以为编程只是写代码。其实远不止如此，编程是在创建一个持续修正、逼近目标的系统。这是我在 [nginx](https://zhida.zhihu.com/search?content_id=778993055&content_type=Answer&match_order=1&q=nginx&zhida_source=entity) 团队多年工作后慢慢理解出来的。
我将以 nginx 这个软件为例，来说说编程难在哪，还有为什么 nginx 能成为世界上最有影响力的 [HTTP 开源软件](https://zhida.zhihu.com/search?content_id=778993055&content_type=Answer&match_order=1&q=HTTP+%E5%BC%80%E6%BA%90%E8%BD%AF%E4%BB%B6&zhida_source=entity)之一。
我们先说目标，也就是要做什么。nginx 功能非常强大，但是为了理解编程到底难在哪，我们简化下它的定义，保留它最核心的：nginx 是一个高稳定、高性能和高安全的代理服务器。
先说说这三高：
高稳定：我以前在一家 CDN 公司，我们用 nginx 做[负载均衡](https://zhida.zhihu.com/search?content_id=778993055&content_type=Answer&match_order=1&q=%E8%B4%9F%E8%BD%BD%E5%9D%87%E8%A1%A1&zhida_source=entity)。如果你不动它，它基本可以像牛马一样，24 小时不停地服务，也不用你操心。稳定就是用着放心。从实现上有个非常重要的细节，也是编程经常被忽略的，就是错误的处理。nginx可以以说任何错误情况都被处理了，而且它的代码没有因为这些非happy path变的凌乱，反而一样的井井有条。它定义了几个通用的宏。
```
NGX_OK, NGX_ERROR, NGX_AGAIN, NGX_DECLINED, NGX_DONE
```
也就是严谨的错误处理让nginx保持非常稳定。
高性能：在 nginx 之前，Apache 几乎是 20 年前的霸主。nginx 应该是在 2007、2008 年左右开始在中国有点名气的。国内不少人对 nginx 的推动做出不少贡献。这里要致敬一个人：张宴。这位工程师在nginx还没在国内火起来之前，写过一篇类似 nginx 性能胜过 Apache 10 倍的文章，在前期推广了 nginx。所以nginx真给很多公司省了不少钱，尤其是那些几千台、几万服务器跑nginx的公司。nginx 是 C 语言写的，但它的性能不只是因为 C，而是把事件驱动、[非阻塞 I/O](https://zhida.zhihu.com/search?content_id=778993055&content_type=Answer&match_order=1&q=%E9%9D%9E%E9%98%BB%E5%A1%9E+I%2FO&zhida_source=entity)、连接管理、内存管理这些工程能力发挥到了极致。
高安全：nginx 也出现过安全问题，但整体来说，它的设计比较克制，安全边界比较清晰，也经受了长期生产环境的验证。
我再举个例子说明 nginx 为什么强大，以及难在哪里。现在不少人用 nginx 当 AI 的代理服务。这里有个细节，实现代理一般有两种，缓冲式：也就是拿到上游完整响应然后再给客户端。流式：边拿上游边给客户端。个人觉得后者实现难度至少是前者的 5 倍以上。首先内存的使用减少了，因为不会积压在服务器，然后响应延迟等也减少了。这都是性能方面的优化。实现上边读上游边写client，你得同时处理两个连接，而且都是异步的，非常复杂。至于为什么 nginx 20 年前就要支持这种，这应该是 Igor Sysoev 的个人工程师直觉吧。
所以**目标决定了编程的难度。**
编程是很难先定义完一个目标，然后一步到底一下子实现的。即使当前目标已经实现了，目标也在不断地改变，因为需求会变化。比如 nginx 早期只支持 HTTP/1，现在支持了 [HTTP/2](https://zhida.zhihu.com/search?content_id=778993055&content_type=Answer&match_order=1&q=HTTP%2F2&zhida_source=entity)、HTTP/3。我感觉正确的做事方式是根据目标不断修正。
我将这个过程拆解成这样：定义目标 -> 计算误差 -> 修正行动。
是不是说新需求进来了，我们把它实现就好了，也就是做修正不就行了，是这样吗？没这么简单的，**正确的修正是减少误差**。如果新增了误差就不对了。
我们来聊为什么直接修正没这么简单。以 nginx 为例。它有连接层 conn 和协议层 http。这个很好理解。我们现在加了 http 的功能，理想情况下只影响 http，不要影响 conn。因为 http 依赖 conn。
现在问题就来了，写代码如果不考虑[架构设计](https://zhida.zhihu.com/search?content_id=778993055&content_type=Answer&match_order=1&q=%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1&zhida_source=entity)，很有可能 conn 和 http 就耦合在一起，甚至没分层。这就造成了修正时可能会新增误差。这也是为什么需要有架构设计，**架构就是在控制复杂度**。
单单这个架构设计就非常难了。这也是 nginx 高稳定性的原因之一，它的架构设计非常好，不然也很难支撑这么多的功能。
所以**这是第一个难，架构设计**，它对作者的原创能力要求非常高。
假如我们架构设计好了，也就是每个模块分层都做得不错，接下来是**第二个难，建模**。
建模是什么呢？现在很多语言都支持[面向对象](https://zhida.zhihu.com/search?content_id=778993055&content_type=Answer&match_order=1&q=%E9%9D%A2%E5%90%91%E5%AF%B9%E8%B1%A1&zhida_source=entity)，简单讲就是那些类，虽然这定义有点粗糙，是为了便于理解。如果你看 nginx 的源码，它里面的结构体非常合理。以限速的实现为例，它有这些结构体：
```
ngx_http_limit_req_node_t
ngx_http_limit_req_shctx_t
ngx_http_limit_req_ctx_t
ngx_http_limit_req_limit_t
ngx_http_limit_req_conf_t
```
因为写代码是实现业务，你需要代码体现业务的信息，这是一定要有的。假如没有这些结构体，你的代码不得不有更多的函数，更多的逻辑来体现。但是有了这些，相关的逻辑就围绕结构体组织得很好。它有一种牵一发而动全身的感觉。还有它非常依赖架构设计。如果架构设计不好，你不得不用更复杂、更多的结构体来实现同样的业务。
假如你在实现复杂的功能时，我觉得这是编程最难的地方，引入必须的模型。即使现在你借助 AI，个人使用上感觉它的水平不如比较专业的程序员。但是 AI 不怕复杂，或者可以说是不同的审美。
我们借用 [Kent Beck](https://zhida.zhihu.com/search?content_id=778993055&content_type=Answer&match_order=1&q=Kent+Beck&zhida_source=entity) 的名言来继续理解：make it work, make it right, make it fast。
我们现在讨论的都是 make it work 和 make it right。其中 make it right 基本跟设计有关，也是比较难的部分。
我们接着说 make it fast 部分，这基本跟性能有关了。
nginx 不止跑得快，它的内存占用也极低，我觉得这是其他软件很难做到的。因为首先它是 C 写的，C 可以控制内存的使用。接着 nginx 非常复杂的一个部分叫 buffer，它是用来处理数据的。它难在它支持了复用，也就是说有些 buffer 用完，没有马上释放，接着继续拿来复用，这就造成代码要非常准确地控制它。而且 buffer 有多种类型，比如有些是文件，有些是网络数据等，还跟模块有关，总之是个非常基础的设施，又遍布代码各个角落。如果你牺牲性能，就可以大幅简化代码。但是 Igor 就是能驾驭这种复杂度。
也就是说，为了在现有资源的约束下追求性能，你不得不引入更复杂的实现。
所以回到最开始的问题：编程到底难在哪里？
语言当然重要，算法当然重要，做事方式也重要。但这些更多是基础能力。真正难的是，你要在一个不断变化的目标里，设计出一个可以持续修正的系统。
这个系统不能只是今天能跑。它还要能承受明天的新需求，能控制修改带来的影响范围，能在性能、稳定性、安全性之间做取舍，能让后来的人继续理解和修改。
这也是为什么我觉得编程不像单纯写文章，更像是在长期维护一个会不断生长的结构。你每次写代码，实际上都在回答几个问题：目标是什么？现在离目标差多少？这次修改是在减少误差，还是在制造新的误差？
能把功能写出来，是 make it work。  
能让系统结构继续保持清晰，是 make it right。  
能在资源约束下把性能做上去，是 make it fast。
这三件事叠在一起，是编程真正难的地方。
