用 AI 永久了，形成了巨大依赖，写任何东西之前，都希望让 AI 先打一份草稿。但久而久之，我担心我的深度思考越来越少，产生挥之不去的脑雾。所以需要逼自己坐下，整理思路做一些输出。
### LLM as Software
我在去年下半年后知后觉意识到，LLM Model 或者所谓的 Agent ，或许是新一轮的计算机革命的开始，类比于互联网和移动互联网（没有用广义的 AI，但很多人现在其实都用 AI 来指代 LLM 或基于 LLM 的 Agent 了）。所以想认真思考这个变化会是什么。
过去我也一直认为，基于 LLM 的 软件其实就是 ChatGPT 套壳，但当我发现所谓的 Agent 的代码都有上万行的时候，我的看法彻底改变了。在吸收了大量播客和博客的文章之后，我开始认同一年多以前，Andrej Karpathy 所谓的 LLM as OS 的论断。
**当你只把 LLM 当做一个普通的 Model，一问一答的时候，它就是一个高级的 ChatBot**。但当你开始打造**上下文工程**（包括 Memory 和 Tool 等），并围绕 LLM 作为一个核心去构建软件的时候，它和过去软件的差异和带来的新的体验就显而易见了（这样的软件也可以被称之为 AI 原生的软件），Cursor 就是一个很好的例子。从这个角度来理解，Agent 其实只是一个 LLM as Software 的一个尤为成功的具象化的例子。LLM 为核心改变的，是传统基于 API 的各部件沟通与固定的事件触发，变为基于自然语言的信息传递与灵活的事件调用。
基于这个想法，我开始探索 Agent 和所谓 AI 原生的 LLM-based Software。而在这个过程中，我也开始适应并探索，新一代的 AI 原生的工作流。
### 基于 LLM 的工作流
我从一开始就是 claude code （下文简称cc）的忠实用户，转变发生在作为几乎零基础 IOS/安卓 开发经验的我，用一下午 prompt cc 做出第一版能看能用的 App 之后。因此后面不管是开发还是一般场景，cc 都是我的 Agent 主力（虽然中间有过和 codex 并轨开发，但从开发场景来说，codex 的响应和效果大部分时候还是敌不过 cc，但有时候交替使用也有奇效，有的任务也是 codex 写出的脚本做的更好，比如对 Excel 表格的操作）。 也正因此，当看到 Meta 花 20 亿买下 Manus 的时候，我尤其不解，甚至认为我的认知有 Gap；我的不解，随着我认知“Manus 是非开发人士的cc”而消解，又随着最近 cc 团队花了一周半完成了 claude work 而再度袭来。
跑题了，从开始使用 cc 之后，我的工作流分为两大块，基于 cc 的自动化 coding agent，这部分仅依赖 human feedback；另一部分是基于 cursor，做人类为主导的所谓 vibe coding。但我逐渐发现，人是懒惰的，我的工作流中，cc 的比重越来越高。
在各种小红书和 B 站视频冲浪中，我学会和尝试了一整套基于 AI 的开发工作流。
### AI 助手拆解需求文档和实现方案
首先，基于一个想法，用尽量详细的语言描述这个想法的方方面面；然后，让 chatgpt 或 claude 输出一份正式的需求文档，人类对需求文档做手动修改，或者 prompt AI 助手再修改和细化，满意之后；再让 AI 助手输出一份详实的实现方案、架构设计和接口定义，在这个过程中，仍然由人类反馈进行修改。最后，提前确定需要的权限，让 cc 开始自动化静默实现（往往还是需要定期监控以确保一切正常）。
### 基于 human feedback 的 coding agent 工作流
当你看到 cc 输出的第一版内容，不管是网站还是 App，你大概率会惊讶于**生产力的提高**，让你的一个粗糙想法，在完全不懂开发的情况下直接成型。但往往，这只是开始，要想实现完整功能，做出可以让他人使用的复杂系统，你的工作才刚刚开始。
一般来说，软件包括前端（ios，web，安卓）和后端（通常还包括数据库和redis），基于 LLM 的软件可能还需要专门的 LLM/agent 模块。首先，你需要逐个实现各个模块，然后调试他们相互连接工作。在这个过程中，你不需要详细查阅代码，而是采用**监督-反馈**的工作模式，在这种工作模式下，你的角色更接近于**产品经理+测试**，尽管你可以让 agent 自己写测试脚本进行测试，但很多上手的体验和功能，还是需要你亲自测试之后才知道实现的情况。
举例来说，当我开发前端网站或者 App 的时候，我往往会**将实现后的截图，连同我对 bug 的描述或我希望提升的细节再 prompt 给 cc**。cc 做的非常好的一点是对于图像的理解非常到位，往往几次交互（很多时候一次，但有时也会引入新的问题）就可以完成你希望的效果。你的**大部分时间，都需要消耗在这样的测试和反馈流程**中，尽管近期 claude 的一些新尝试，例如 connector （claude-chrome插件等），旨在通过将 claude 连接到浏览器（未来可能是 xcode 以及 android studio）来闭环这个反馈 loop，很多事情，在没有 reference 或 reference 不完全的情况下，人类的主观介入和 feedback 循环是不可避免的。
### 黑盒开发和它带来的问题
尽管新的工作流带来了效率上的质的提升，但它实际上容易形成一套新的黑盒开发的流程，即项目开发者不关心具体实现，只关心最后结果，而这也引入了很多新的问题。
### 不可维护性和 Agent 的依赖性
当系统是**简单、一次性、浅逻辑的时候，你大多时候不需要担心 cc 开发出的产品的完整度，因为它不需要再被维护了**，你也不需要再了解更多实现细节。这也是为什么我们在社交平台上看到的大部分人，宣传 Agent 带来的实现变化的时候，用到的例子往往都是非常浅的交互逻辑。
但是，当你开始长期维护一个项目，其涉及到的技术栈丰富，部件众多且需要深入的交互逻辑时，你会逐渐发现放手 Agent 开发带来的问题：你的项目几乎很难由你维护了！你会发现，由于你没有从开头就介入代码的开发，你完全不知道该从哪里开始 debug 和接手。在这之后，你只能不得不继续依赖 agent：1. 求助 agent 帮你总结项目结构； 2. 继续反馈你发现的 bug，让 agent 帮你修复。
### 只增不减的屎山
随着项目的迭代和开发，**你的代码会以比你自己开发更快的速度堆砌成一座屎山**。具体表现为
1. 因为上下文太长，Agent 无法充分理解自己过去的代码以致于 Agent 写出误导性的注释
2. 为了实现新功能，Agent 不考虑现有项目结构，写出让人和 Agent 都 confuse 的代码/变量名/数据项
3. Agent 为没有实现的新功能提前实现占位符和数据库
4. 误导性的内容在之后被 Agent 错误理解基于错误的名称实现新功能，例如误导性的注释，confuse 的数据项，没有实现的功能等，如此循环。
而由于项目的不可维护性，你需要花更多时间和 Agent 交互让 Agent 和你都充分理解误导性的内容，认识到错误。一个具体的例子是，我在引入一个新功能组件的时候，由于一直无法测试通过，我花了整整一个周末让 Agent 帮我寻找错误和理解已有的代码，并通过 Agent 前后输出相互矛盾的地方定位错误；最后，又花了整整一天，prompt cc 清理错误的实现和 confuse 的代码。在这个过程中，虽然我没有写任何代码，但是付出的时间和精力都是可观的（token的消耗更是可观的）。
### 只关注结果的浮躁心态
除了物质层面，还有人的精神层面的变化。由于**结果比过程更容易拿到了，你会更关注结果的正确性而非过程的正确性，有时即便是冗余、低效的实现，也会被结果的正确性而接受**。这导致人更加浮躁，忽略了实际上正确的、高效的实现才是理想结果的主要成因，你会更想一步登天，而更不愿意投入精力深入实现的细节，抽丝剥茧。虽然有些项目很快地完成了，但事后总结，你会发现个人的技术栈并没有得到提高；甚至由于技术方案设计也是依赖 AI 助手，你对方案的理解和把控，也仅局限于 AI 总结的部分，甚至给人带来脑雾。
### 新范式下的要求
新的自动化开发范式在提高生产力的同时，对人的角色和能力又提出了新的要求：
1. 产品经理和功能测试日趋重要，它决定了产品的实际用途和实际体验
2. 仍需要把握所需技术栈，并要尽可能多介入 Agent 的开发流程，理解实际的实现方式，打破黑盒开发。但是，由于 Agent 的输出速度在逐渐增加，而人的吸收速度是有限的，这个要求其实很高。不过，好的方面是，现在可以**用 ChatGPT 辅助学习，而不再需要 Stack Overflow 和 CSDN 反复查询答案了**，学习效率也是成倍增加。
在新的生产力革命前，我们仍需要不断认真思考和迭代认知，如何利用好生产力，而又不被生产力所吞噬与埋没。
