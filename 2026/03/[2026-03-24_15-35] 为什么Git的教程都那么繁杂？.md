# 为什么Git的教程都那么繁杂？

---

> 我工作十几年了，就只用了十几个[Git](https://zhida.zhihu.com/search?content_id=774064369&content_type=Answer&match_order=1&q=Git&zhida_source=entity)命令，够用了。
Git的命令有几百个，很多教程恨不得从底层对象模型讲起，[blob](https://zhida.zhihu.com/search?content_id=774064369&content_type=Answer&match_order=1&q=blob&zhida_source=entity)、[tree](https://zhida.zhihu.com/search?content_id=774064369&content_type=Answer&match_order=1&q=tree&zhida_source=entity)、commit、DAG图一通画，看完直接头晕。
实际工作中根本用不到那么多东西。我做了十几年开发，真正在终端里敲过的Git命令，数来数去就那么十来个。按使用场景分，一共5类：日常提交、分支管理、撤销回退、合并、以及偶尔用一次的cherry-pick。下面逐个说。
### 日常提交
每天用得最多的就这几个命令，拉取最新代码、写完代码提交推送，整个流程就是status,pull、add、commit、push。
```
git status
git pull
git add *
git commit -m "修复用户登录校验的空指针问题"
git push origin
```
`git status` 查看当前工作区的状态，哪些文件改了、哪些文件是新增的、哪些已经加到暂存区了，一目了然。add之前先status看一眼，确认要提交的内容没问题，是个好习惯。
`git pull` 从远程拉取最新代码并合并到本地。团队协作的时候，push之前先pull一下是个好习惯，避免和别人的提交产生冲突。如果pull下来发现有冲突，处理方式和merge冲突一样，手动解决后再add、commit。
`git add *` 把当前目录下所有改动的文件加到暂存区。如果只想提交某一类文件，可以用通配符，比如 `git add *.java` 只加Java文件。
这里有个细节值得说一下。`git add *` 和 `git add .` 有点区别：`git add .` 会把当前目录及子目录下所有变更都加进去，包括删除的文件；`git add *` 是shell层面的通配展开，不会包含以点号开头的隐藏文件，删除的文件也不一定能捕获到。日常使用差别不大，知道有这个区别就行。
`git commit -m` 后面跟提交信息。提交信息写清楚改了什么，别写「update」「fix bug」这种等于没说的话。两个月后你自己看git log，会感谢现在写清楚的自己。
`git push origin` 推到远程。如果当前分支已经关联了远程分支，直接 `git push` 也行。
### 分支管理
团队协作离不开分支。日常用到的分支命令就这几个：
```
# 查看本地有哪些分支
git branch
# 查看远程有哪些分支
git branch -r
# 切换到某个分支
git checkout dev
# 删除本地分支
git branch -D feature-login
```
`git branch` 不带参数，列出本地所有分支，当前分支前面会有个星号标记。加 `-r` 看远程分支，加 `-a` 本地和远程一起看。
`git checkout` 切换分支。有一点需要注意：如果当前分支有修改还没提交，且这些修改和目标分支存在冲突，Git会拒绝切换，提示你先处理掉。要么先commit，要么用 `git stash` 暂存起来。
`git branch -D` 强制删除不再使用的本地分支。用大写 `-D` 是因为小写 `-d` 会检查这个分支是否已经合并到当前分支，没合并的话会拒绝删除。大写 `-D` 不管有没有合并，直接删。日常用 `-D` 更省事。
### 撤销和回退
写错了代码想撤回，或者提交了不该提交的东西想回退，这是每个开发者都会遇到的场景。根据情况不同，用到的命令也不同。
**改了文件，还没add，想恢复原样：**
```
git checkout UserService.java
```
这条命令把指定文件恢复到最近一次commit的状态。改了半天发现思路不对，直接用这个命令扔掉所有改动。注意，恢复之后改动就没了，找不回来。
**所有本地改动全部不要了，回到最近一次commit的干净状态：**
```
git reset --hard
```
这个命令会把工作区和暂存区的所有改动全部清掉，回到HEAD指向的那次提交的状态。用之前确认一下，别把有用的改动也丢了。
**已经commit了，想回退到上一个提交：**
```
git reset --hard HEAD^
```
`HEAD^` 表示上一个提交。如果要回退两个提交，用 `HEAD~2`，以此类推。这个操作会把commit记录也干掉，本地的代码回到指定提交的状态。
回退之后，本地的提交历史比远程的要旧。这时候直接push会被拒绝，因为远程有你本地没有的提交。需要强制推送：
```
git push -f
```
**`git push -f`** 是危险操作。它会用本地的提交历史强行覆盖远程的。如果别人已经基于你要覆盖的那些提交做了开发，他们的代码就会出问题。在自己独占的分支上用没问题，在多人协作的分支上用之前，一定要和团队确认。
### 合并
开发完一个功能，要把功能分支合并到主分支，用merge：
```
# 先切到目标分支
git checkout master
# 把功能分支合并过来
git merge feature-login
```
如果两个分支改了同一个文件的同一个位置，Git没法自动合并，会提示冲突。打开冲突文件，会看到类似这样的标记：
```
<<<<<<< HEAD
当前分支的代码
=======
要合并进来的分支的代码
>>>>>>> feature-login
```
手动选择保留哪部分代码（或者两边都保留），把标记符号删掉，然后add、commit就完成了。
如果冲突太多搞不定，或者发现不应该合并，可以终止：
```
git merge --abort
```
这条命令会把合并操作撤销，回到合并之前的状态。是一个很安全的退路。
### Cherry Pick
cherry-pick在日常开发中不算常用，但有些场景离了它还真不行。
典型场景：线上有个bug，你在dev分支上修了，提交了一个commit。现在需要把这个修复也放到release分支上，但不想把dev上其他还没经过测试的代码一起带过去。这时候就用cherry-pick，只把那一个commit搬过去。
```
# 先找到那个commit的哈希值
git log --oneline
# 切到目标分支
git checkout release
# 把指定commit搬过来
git cherry-pick a1b2c3d
```
cherry-pick可以一次搬多个commit，空格分隔就行：
```
git cherry-pick a1b2c3d e4f5a6b
```
如果搬过来的commit和目标分支有冲突，处理方式和merge冲突一样，手动解决后add、commit。
### 速查表
| 场景 | 命令 | 作用 |
| --- | --- | --- |
| 查看 | git status | 查看工作区状态，哪些文件有改动 |
| 同步 | git pull | 拉取远程最新代码并合并 |
| 提交 | git add \* | 暂存所有改动文件 |
| 提交 | git add \*.java | 只暂存Java文件 |
| 提交 | git commit -m "信息" | 提交到本地仓库 |
| 提交 | git push origin | 推送到远程仓库 |
| 分支 | git branch | 查看本地分支 |
| 分支 | git branch -r | 查看远程分支 |
| 分支 | git checkout 分支名 | 切换分支 |
| 分支 | git branch -D 分支名 | 强制删除本地分支 |
| 撤销 | git checkout 文件名 | 恢复单个文件到最近一次提交 |
| 回退 | git reset --hard | 丢弃所有本地改动 |
| 回退 | git reset --hard HEAD^ | 回退到上一个提交 |
| 回退 | git push -f | 强制推送（覆盖远程历史） |
| 合并 | git merge 分支名 | 合并指定分支到当前分支 |
| 合并 | git merge --abort | 终止合并，回到合并前状态 |
| 搬运 | git cherry-pick 提交哈希 | 把指定提交搬到当前分支 |
### 小结
Git命令确实很多，但日常开发真正用到的就这些。提交三件套处理每天的代码推送，分支命令管理多人协作的工作流，撤销和回退解决各种「写错了」「提错了」的问题，merge处理分支合并，cherry-pick偶尔用来跨分支搬运提交。**把这十几个命令用熟，足以应对工作中99%的场景。** 遇到更复杂的操作再现查就行，没必要提前把整本Git手册背下来。
我这十几年来，真就只用了上面的命令。像git stash这种，我都基本没用到。
